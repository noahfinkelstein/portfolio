### [high] Mobile menu is cut off and unscrollable on short viewports (landscape phones)

`src/components/layout/Navbar.module.css:141`

.menu is `position: fixed; inset: 0; display: flex; flex-direction: column; justify-content: center; gap: 3rem; padding: calc(var(--nav-h) + 1rem) var(--gutter) 2rem` with no `overflow-y`, and Navbar.tsx line 106 sets `body.style.overflow = "hidden"` while it is open. The menu's content is taller than many viewports that get it (burger shows at <=800px): five .menuLink items at 1.75rem with inherited 1.6 line-height are 44.8px each (5 x 44.8 + 4 x 36px gap = 368px), plus the 3rem gap and the two-row .full ThemeSwitcher (2 x 40px + 8px = 88px), plus 92px top and 32px bottom padding = about 628px (596px at <=480px). A phone in landscape is 360-430px tall and 640-800px wide, so the menu overflows by 170-270px; `justify-content: center` pushes half above the top edge and half below the bottom, and nothing can scroll, so Home/About at the top and the theme switcher at the bottom are unreachable.

**Fix:** Do it, but prefer auto margins on the existing children over a wrapper div or `safe center`, so no DOM changes and no browser-support gap. In src/components/layout/Navbar.module.css: (1) in `.menu` (line 141) change `justify-content: center` to `justify-content: flex-start` and add `overflow-y: auto; overscroll-behavior: contain;` (the project already uses overscroll-behavior in Latest.module.css:15, and the global `::-webkit-scrollbar` / `scrollbar-width` rules in globals.css:363-382 apply to every element, so the menu's scrollbar is automatically themed); (2) in `.menuLinks` (line 167) add `margin-top: auto;`; (3) add `.menuSwitcher { margin-bottom: auto; }`. In src/components/layout/Navbar.tsx line 194 pass it: `<ThemeSwitcher variant="full" className={styles.menuSwitcher} />` (ThemeSwitcher already accepts className and appends it to the fieldset). Auto margins on the first and last flex items split the free space equally, so the group stays centred exactly as today whenever it fits, and they collapse to 0 when it overflows, at which point the menu starts under the bar's 92px padding and scrolls. Keep the existing padding. Do not rely on `justify-content: safe center` as the mechanism: an unsupported value is discarded and the cascade keeps the current `center`, so Chrome before 115 (mid-2023) and other older engines would stay broken, whereas auto margins work everywhere. Side benefit: focused links now scroll into view inside the menu for the Tab trap at lines 116-130.

### [medium] Home-page entrance animations are consumed on client navigation because ScrollTriggers are created before Next resets the scroll position

`src/lib/gsap.ts:37`

`useGsap` runs its setup in `useIsomorphicLayoutEffect`, so every `gsap.from(..., { scrollTrigger: { toggleActions: "play none none none" } })` in SectionHeader.tsx (line 59), Reveal.tsx (line 57) and LatestRow.tsx (line 278) is created in React's layout phase. Next's scroll-to-top for a `<Link>` navigation happens later in the same phase, in the ancestor `InnerScrollAndFocusHandler.componentDidMount/componentDidUpdate` (layout-router.js, `htmlElement.scrollTop = 0`), and parent class lifecycles run after children's layout effects. On `/projects -> /` (e.g. the "<- Home" PageSelect at the bottom of /projects, scrollY of several thousand px) each trigger initialises with the stale scroll: ScrollTrigger's first `update()` sees `clipped > 0` with `prevProgress = 0`, picks the enter toggle and calls `animation.play()`. Next then scrolls to 0, a leaveBack with action `none`, so the tween stays at its end state. After the designed round trip the "Selected Projects", "About Me", "Experience" headers, the About photo/text slide-in and the journey box stagger are already visible and never animate on scroll. (CardReveal uses a passive `useEffect` and the Titles scrub re-syncs, so they are unaffected.)

**Fix:** In src/lib/gsap.ts keep useIsomorphicLayoutEffect but defer the context creation one frame and cancel it in cleanup:

export function useGsap(setup, deps = [], scope) {
  useIsomorphicLayoutEffect(() => {
    // Next scrolls the new page (to the top, or to the URL hash) in an
    // ancestor's componentDidMount/Update, which React runs after this
    // layout effect. Creating ScrollTriggers here would read the previous
    // page's scroll position and "play" every from-tween already past it,
    // so the context is created one frame later, still before first paint.
    let context: gsap.Context | undefined;
    const frame = window.requestAnimationFrame(() => {
      context = gsap.context((self) => setup(self), scope?.current ?? undefined);
    });
    return () => {
      window.cancelAnimationFrame(frame);
      context?.revert();
    };
  }, deps);
}

Also update the header comment (lines 10-13) so the "across client navigations" promise explains the deferral. No change is needed in SectionHeader.tsx, Reveal.tsx, LatestRow.tsx or Titles.tsx. Do not switch to plain useEffect: for the nav's "/#about" link (src/content/site.ts:76) React paints the transition before passive effects run, which would show the About section fully visible for a frame before it is hidden and slid in.

### [medium] After a WebGL context loss the torus stays invisible even once the context is restored

`src/components/hero/torusScene.ts:406`

`handleContextLost` (lines 406-410) calls `this.stop()` and sets `this.canvas.style.opacity = "0"`, but no `webglcontextrestored` listener is registered (only `webglcontextlost`, line 392, removed at 561). three.js's own `onContextRestore` re-initialises GL state but does not restart the loop that `stop()` cancelled with `setAnimationLoop(null)`. The next `wake()` (scroll, theme change, tab visible) restarts `update()`, but canvas opacity is only rewritten when the rounded value differs from `this.lastOpacity` (lines 699-704), which still holds the pre-loss value. In the hero (progress 0) and the dock (progress 1) the computed opacity is constant, so the style stays at "0": the knot never reappears and the "Back to top" dock button (TorusField.tsx line 166) renders as an empty translucent circle. Context loss on backgrounded tabs is routine on iOS Safari and Android Chrome, and the tab-hidden path (`setPageVisible(false)` -> `stop()`) is exactly where it happens.

**Fix:** Do it as proposed in src/components/hero/torusScene.ts: add `private handleContextRestored = () => { this.lastOpacity = -1; if (this.reduced) this.redrawIfIdle(); else this.wake(); };` next to handleContextLost, register it with `canvas.addEventListener("webglcontextrestored", this.handleContextRestored)` at line 392 and remove it at line 561 (before forceContextLoss). The extra `this.lastOpacity = -1` inside setPageVisible(true) is optional: the restored handler alone covers both orderings of visibilitychange and webglcontextrestored (wake() is a no-op while hidden and the reset survives until the next update()), so you can drop it to keep the change minimal, or keep it since it costs one style write per tab return. Also add one line to the header comment's "Cost control" paragraph noting that a lost context hides the canvas and a restored one brings it back.

### [medium] The background glow (--glow) never paints in any theme

`src/app/globals.css:269`

`body::before` is `position: fixed; inset: 0; z-index: -1; background: var(--glow)`. Because `html` has its own opaque `background-color: var(--bg)` (line 244), the body's `background-color: var(--bg)` (line 258) is not propagated to the canvas and is painted as an ordinary block background, which the root stacking context paints after negative-z-index descendants. So the fixed glow is drawn under body's opaque background and is invisible in Night, Cyan, Terminal and Paper alike. Reproduced with the exact html/body/::before rules in a standalone page in Chromium: no glow; adding `isolation: isolate` to body makes it appear. The README and TorusField comments both assume the glow is visible behind the hero canvas.

**Fix:** Do it as proposed, with these specifics. In src/app/globals.css add `isolation: isolate;` to the `body` rule (lines 250-265) with a one-line comment such as "/* Own stacking context, so the ::before glow paints above body's background instead of under it (html also has a background, so body's is not propagated to the canvas). */". Prefer this over `position: relative; z-index: 0` (which would also turn body into the containing block for absolutely positioned descendants such as .sr-only, needlessly) and over deleting `html { background-color }` (which works too, but html's background is useful belt-and-braces for the canvas/overscroll color and the print override). Because the glow has never actually been visible, after the change load the home page once in each of Night, Cyan, Terminal and Paper and confirm the top-left glow reads as intended under the hero and the 95%-opaque nav; the per-theme alphas were set blind, so adjust them if any theme looks too strong (the loader is opaque --bg at z 100, so the intro is unaffected). No other file needs to change.

/** Media with a pointer-only link over it. The button is the keyboard and
 *  screen-reader route, so the overlay is hidden from both; the media itself
 *  stays in the tree so its alt text is announced. */
function MediaLink({ link, children }: { link?: ProjectLink; children: React.ReactNode }) {
  if (!link) return <>{children}</>;

    <div className={styles.mediaWrap}>
      {children}
      <a
        className={styles.mediaOverlay}
        href={link.href}
        tabIndex={-1}
        aria-hidden="true"
        {...(external ? { target: "_blank", rel: "noopener" } : {})}
      />
    </div>
  );
}
